# AWS CI/CD Deployment Guide

This guide describes a GitHub Actions pipeline that builds this repository's Docker image, publishes it to Amazon ECR, and deploys it to Amazon ECS on AWS Fargate. It is written for the application in this repository; it does not deploy the Azure resources under `infrastructure/`.

## 1. How this application runs

- `app.py` starts a FastAPI application on `0.0.0.0:8080`.
- `GET /predict` renders the prediction form and is a suitable HTTP health-check path. `GET /train` starts model training, so do not use it as a health check.
- At application import time, `MONGO_DB_URL` must be set. The application reads training data from MongoDB Atlas.
- S3 access is through `boto3`'s normal AWS credential chain. The model bucket and key are currently constants in `shipment/constant/__init__.py`; the bucket is `ship-price-io-files` and the model filename is `shipping_price_model.pkl`.
- The existing `.github/workflows/main.yml` deploys to Azure Container Registry and Azure Web App. The Terraform under `infrastructure/` is Azure-specific. Add a separate AWS workflow rather than treating those files as AWS configuration.

## 2. Important preparation and security changes

Do these before building a production image:

1. **Do not pass AWS or MongoDB credentials as Docker build arguments.** The current `Dockerfile` declares secret-related `ARG` and copies them into image `ENV` values. Build arguments and image environment metadata can be exposed through image inspection, caches, or build logs. Remove the `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION`, and `MONGO_DB_URL` arguments and their corresponding `ENV` lines. Do not replace them with hard-coded values. Supply `MONGO_DB_URL` at task runtime from AWS Secrets Manager, and grant the ECS task an IAM role for AWS access.
2. **Replace the old Python base image.** The current Dockerfile uses Python 3.7 on Debian Buster, both end-of-life. Move to a currently supported Python slim image after checking that the project's dependencies install and run on that Python version. For example, the Dockerfile should follow this shape (choose and verify the supported Python tag for your deployment):

   ```dockerfile
   FROM python:3.11-slim
   WORKDIR /app
   ENV PYTHONDONTWRITEBYTECODE=1 \
       PYTHONUNBUFFERED=1
   COPY requirements.txt .
   RUN pip install --no-cache-dir -r requirements.txt
   COPY . .
   EXPOSE 8080
   CMD ["python", "app.py"]
   ```

3. Keep `.env`, credentials, local datasets, virtual environments, notebooks, and generated artifacts out of the Docker build context. Review `.dockerignore` and only add exclusions that will not omit runtime files needed by the app.
4. Verify the app can start with `MONGO_DB_URL` set and that `GET /predict` returns HTTP 200. Dependency compatibility and the image build should be checked before enabling automatic production deployment.

## 3. Create AWS resources

Use an AWS account and region in which you can create IAM, ECR, ECS, Secrets Manager, CloudWatch Logs, and networking resources.

### 3.1 Create the ECR repository

Create a private ECR repository for the application, for example `shipment-pricing`. Enable image scanning on push and consider tag immutability. Note the AWS region, account ID, and repository name; the registry URI is:

```text
<AWS_ACCOUNT_ID>.dkr.ecr.<AWS_REGION>.amazonaws.com/shipment-pricing
```

### 3.2 Store the MongoDB connection string

1. In AWS Secrets Manager, create a secret containing the MongoDB Atlas connection URI.
2. Copy the secret ARN. Configure MongoDB Atlas network access so the ECS tasks can reach the cluster. Prefer a private network connection or a narrowly controlled egress address; do not allow access from every IP address for convenience.
3. The task definition will expose the secret to the container under the exact environment-variable name `MONGO_DB_URL`.

The app reads `MONGO_DB_URL` immediately on import, so the task must receive it before the process starts. A misspelled or absent variable prevents the app from starting.

### 3.3 Prepare S3 and task IAM roles

The application uses the existing bucket name `ship-price-io-files`. Ensure it exists in the region/network appropriate for the app, and that the required model object is present before serving predictions. If using another bucket, update the application constant and deploy that code change as well.

Create the following roles:

- **ECS task execution role:** trusted by `ecs-tasks.amazonaws.com`, with the standard `AmazonECSTaskExecutionRolePolicy`. Add `secretsmanager:GetSecretValue` for only the MongoDB secret ARN (and `kms:Decrypt` for its customer-managed key, if applicable). This role lets ECS pull the image, write logs, and fetch injected secrets.
- **ECS task role:** trusted by `ecs-tasks.amazonaws.com`, with narrowly scoped S3 access. Grant `s3:ListBucket` on `arn:aws:s3:::ship-price-io-files` and `s3:GetObject` / `s3:PutObject` on `arn:aws:s3:::ship-price-io-files/*` as needed. Prediction requires reading the model; training/model publishing also writes model and data artifacts. Do not place long-lived AWS access keys in GitHub or the container.

### 3.4 Create the ECS/Fargate service and network

1. Create an ECS cluster using Fargate capacity.
2. Create a task definition for Linux/Fargate with `awsvpc` networking, a supported CPU/memory size, the task execution role, and the task role.
3. Set the container's port mapping to TCP `8080`. Configure CloudWatch Logs for the container.
4. Create or select a VPC with at least two subnets in separate Availability Zones. Tasks need outbound access to MongoDB Atlas, ECR, CloudWatch Logs, and S3. Use private subnets with a NAT gateway and/or the appropriate VPC endpoints. Confirm security group and route-table rules permit this traffic.
5. Create an Application Load Balancer (ALB), a target group of target type **IP**, and an ECS service attached to that target group. Configure the target group health check path as `/predict` and its port as traffic/8080. The task security group should accept port 8080 only from the ALB security group. Expose HTTP/HTTPS on the ALB; use HTTPS with an ACM certificate for a public production endpoint.
6. Configure desired task count, deployment circuit breaker/rollback, and (optionally) autoscaling. Start with a single task for a basic test, then size and scale based on measured load.

## 4. Configure GitHub Actions OIDC access

Use GitHub's OIDC federation instead of static AWS access keys:

1. In IAM, add GitHub Actions as an OIDC identity provider if it is not already configured. The provider URL is `https://token.actions.githubusercontent.com` and the audience is `sts.amazonaws.com`.
2. Create a deploy role whose trust policy allows `sts:AssumeRoleWithWebIdentity` only for your GitHub organization/repository and the intended branch or GitHub Environment. A typical subject restriction is `repo:<OWNER>/<REPOSITORY>:ref:refs/heads/main`; adjust it if using a protected `production` environment.
3. Give this role only the CI permissions needed for this pipeline:
   - ECR authentication (`ecr:GetAuthorizationToken`) and push operations (`ecr:BatchCheckLayerAvailability`, `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`, `ecr:CompleteLayerUpload`, `ecr:PutImage`) scoped to the target repository where supported.
   - `ecs:DescribeTaskDefinition`, `ecs:RegisterTaskDefinition`, `ecs:DescribeServices`, and `ecs:UpdateService` for the deployment and service-stability wait.
   - `iam:PassRole` restricted to the ECS task execution and task roles.
4. In the GitHub repository, add these **Actions variables** (Settings → Secrets and variables → Actions → Variables):

   | Variable | Example/value |
   | --- | --- |
   | `AWS_REGION` | `us-east-1` |
   | `AWS_ROLE_ARN` | ARN of the GitHub Actions deploy role |
   | `ECR_REPOSITORY` | `shipment-pricing` |
   | `ECS_CLUSTER` | ECS cluster name |
   | `ECS_SERVICE` | ECS service name |
   | `ECS_TASK_DEFINITION` | `aws/task-definition.json` |

   Use a protected GitHub Environment for production approvals if appropriate. No AWS access key variables are required.

## 5. Add an ECS task definition to the repository

Create `aws/task-definition.json` and replace the example values with your AWS account and region values. Keep the MongoDB connection URI out of this file; ECS obtains it from Secrets Manager.

```json
{
  "family": "shipment-pricing",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "1024",
  "memory": "2048",
  "executionRoleArn": "arn:aws:iam::<AWS_ACCOUNT_ID>:role/ecsTaskExecutionRole",
  "taskRoleArn": "arn:aws:iam::<AWS_ACCOUNT_ID>:role/shipmentPricingTaskRole",
  "containerDefinitions": [
    {
      "name": "shipment-pricing",
      "image": "IMAGE_PLACEHOLDER",
      "essential": true,
      "portMappings": [
        {
          "containerPort": 8080,
          "protocol": "tcp"
        }
      ],
      "secrets": [
        {
          "name": "MONGO_DB_URL",
          "valueFrom": "arn:aws:secretsmanager:<AWS_REGION>:<AWS_ACCOUNT_ID>:secret:<SECRET_NAME>"
        }
      ],
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/shipment-pricing",
          "awslogs-region": "<AWS_REGION>",
          "awslogs-stream-prefix": "ecs"
        }
      }
    }
  ]
}
```

Create the CloudWatch log group `/ecs/shipment-pricing` in the same region before deployment, or configure the execution role to create it. Replace `IMAGE_PLACEHOLDER` automatically in the workflow below.

## 6. Add the AWS deployment workflow

Create `.github/workflows/aws-deploy.yml`. This workflow builds an image tagged with the commit SHA, pushes it to ECR, registers a new task-definition revision, and updates the ECS service. It deliberately does not pass application secrets during the Docker build.

```yaml
name: Build and deploy to AWS ECS

on:
  push:
    branches: [main]

permissions:
  contents: read
  id-token: write

env:
  AWS_REGION: ${{ vars.AWS_REGION }}
  ECR_REPOSITORY: ${{ vars.ECR_REPOSITORY }}
  ECS_CLUSTER: ${{ vars.ECS_CLUSTER }}
  ECS_SERVICE: ${{ vars.ECS_SERVICE }}
  ECS_TASK_DEFINITION: ${{ vars.ECS_TASK_DEFINITION }}
  CONTAINER_NAME: shipment-pricing

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Check out source
        uses: actions/checkout@v4

      - name: Configure AWS credentials with OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}

      - name: Log in to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build and push image
        id: build-image
        env:
          REGISTRY: ${{ steps.login-ecr.outputs.registry }}
          IMAGE_TAG: ${{ github.sha }}
        run: |
          docker build --pull -t "$REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG" .
          docker push "$REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG"
          echo "image=$REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG" >> "$GITHUB_OUTPUT"

      - name: Render task definition
        id: render-task-definition
        uses: aws-actions/amazon-ecs-render-task-definition@v1
        with:
          task-definition: ${{ env.ECS_TASK_DEFINITION }}
          container-name: ${{ env.CONTAINER_NAME }}
          image: ${{ steps.build-image.outputs.image }}

      - name: Deploy to Amazon ECS
        uses: aws-actions/amazon-ecs-deploy-task-definition@v2
        with:
          task-definition: ${{ steps.render-task-definition.outputs.task-definition }}
          service: ${{ env.ECS_SERVICE }}
          cluster: ${{ env.ECS_CLUSTER }}
          wait-for-service-stability: true
```

For production, pin third-party GitHub Actions to reviewed commit SHAs and maintain those pins. Protect the `main` branch and `production` environment, and require review/CI checks before changes can deploy. Add a separate pull-request workflow for tests and image-build validation so changes are checked before merging.

## 7. First deployment and verification

1. Confirm ECR, ECS cluster/service, task definition roles, Secrets Manager secret, CloudWatch log group, ALB target group, subnets, and security groups are configured.
2. Confirm the configured ECS service has the expected task definition family and is attached to the ALB target group.
3. Push or merge a small verified change to `main`. In GitHub Actions, confirm each step succeeds and that the ECS service reaches a stable state.
4. In the AWS console, check ECS service events and running task health. If a task stops, inspect its stopped reason and the container's CloudWatch log stream.
5. Open the ALB DNS name in a browser and confirm `/predict` renders the prediction page. Submit a test prediction only after a compatible trained model exists in S3.
6. Confirm the target group reports healthy targets. Verify logs do not contain the MongoDB URI or AWS credentials.
7. Test a controlled rollback by redeploying a known-good task-definition revision, or use the ECS deployment circuit breaker to roll back an unhealthy release.

## 8. Ongoing operation and troubleshooting

- **Task exits immediately:** inspect CloudWatch logs. Check `MONGO_DB_URL`, Python/dependency compatibility, the container command, and that files such as `templates/` and `static/` were included in the image.
- **Task cannot pull the image or write logs:** check the task execution role, ECR repository/region, and task network access to ECR and CloudWatch Logs.
- **Application reports S3 access errors or cannot load a model:** check the task role (not the execution role), bucket name, object key, S3 region, and task-to-S3 network path. Ensure the expected model was uploaded before enabling predictions.
- **MongoDB connection times out:** verify Atlas network access, DNS/egress from the task subnets, credentials in Secrets Manager, and any IP allow list.
- **ALB reports unhealthy targets:** confirm container and target group port 8080, task security-group ingress from the ALB, and health check path `/predict`. Do not configure the check to call `/train`.
- **Deployment remains in progress:** check ECS service events, available subnet IPs, desired/running task counts, and target group health. The Actions deploy step waits for service stability and may fail if the service cannot become healthy.
- **Application image or model is vulnerable/stale:** rebuild from a maintained base image, review dependency updates, and enable ECR image scanning. Use immutable image tags or deploy by digest when stronger provenance is required.

## 9. Cost and cleanup

Fargate tasks, ALB, NAT gateways, ECR image storage, CloudWatch Logs, and S3 can incur charges. Set log retention and ECR lifecycle policies, monitor AWS Budgets, and right-size the service after observing resource use. To stop ongoing charges, scale the ECS service to zero or delete the service and separately remove unused load balancers, NAT gateways, ECR images/repository, log groups, and other resources. Do not delete the MongoDB secret or model bucket until their data is no longer needed.
